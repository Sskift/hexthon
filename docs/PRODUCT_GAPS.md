# 产品差距与可借鉴方案

核查日期：2026-11-02。Hexthon 基线为 v0.2.2 默认接口模式。下文的竞品能力是官网、帮助中心或发布说明中的公开宣称，并非已在本机腾讯国服验证；“未核实”不表示对方一定没有。商业产品的采集实现没有公开时，不推测它使用了截图、进程内存或某个 SDK。

## Hexthon 仍缺少什么

| 优先级 | 缺失或不完整的能力 | 当前情况与完成标准 |
| --- | --- | --- |
| P0 | 无截图读取三选一、刷新与选中事件 | 默认模式没有可靠候选来源。需要实际收到候选、重随、选择、关闭事件，能排除上一轮数据；按等级估计弹窗时间不能替代这些事件。 |
| P0 | 完整已选海克斯与恢复 | 技能字段仅覆盖少数强化。还缺普通被动、替换／转化后的更新、重启及重连恢复；必须区分“已确认”“部分可读”“未知”。 |
| P0 | 场景触发与合理位置 | 默认没有浮层。需要把当前卡片事件与可验证的显示区域关联，选完即隐藏；商店打开状态要单独解决。窗口可置顶不等于知道商店或卡片在哪里。 |
| P1 | 装备与海克斯的完整构筑推理 | 当前只实现有限的装备对策规则和基础强化适配分。还缺任务依赖、装备消耗、转换／替换、互斥、流派切换，以及可靠的完整己方强化上下文。没有可靠来源时不能声称知道敌方强化。 |
| P1 | 原生商店推荐集 | 已有纯数据生成与保留其他装备页的合并函数，未接入写入。需验证国服读写、读回、恢复及本局是否热更新。 |
| P1 | 可核查的胜率、样本量与阵容模型 | OP.GG 页面目前只采用能核实的档位、排名和路线。缺少已核实胜率／样本量；职业标签的阵容修正不等于“最优五人阵容”或获胜概率。 |
| P1 | 国服与性能验证 | 尚无多局事件完整性记录、分辨率／缩放／多屏验证矩阵或帧时间对照。不能用“API 模式”推导零开销。 |
| P2 | 正式分发与维护 | 当前源码启动可用；仍需可靠签名发布、更新和回退、版本不兼容诊断，以及游戏更新后的快速验证。 |

上述差距依据 [README](../README.md) 和当前实现。已具备的基础包括自动跟随英雄、选人己方阵容与共享备选池、双方装备、OP.GG 缓存、自绘面板，以及未知数据保护。当前敌方护甲／魔抗／吸血装备与己方重伤覆盖可触发有限规则建议；不能把这层能力描述为完整实时优化器。

## 建议采用的结构

以下是根据已核实功能和项目约束提出的设计建议，不是对竞品未公开源码的描述：

1. **把信息来源和显示方式分开。** LCU 负责选人／阶段，Live Client 负责已公开装备；Overwolf 若实验成功，只补上它实际提供的事件。OP.GG 保持统计和推荐路线来源。
2. **按局保存事件状态。** 候选、重随、已选、替换、结束分开处理；启动时标明历史是否完整。只收到“最近选中”不能推导完整历史。
3. **有事件才显示。** 强化提示贴近三张卡，关闭即隐藏。商店状态与坐标要独立验证，不能用三选一事件或 Tab 计分板事件代替。
4. **推荐给出可检查的理由。** 区分 OP.GG 档位、统计胜率和本地规则分；说明是哪件敌方装备、哪个已知强化或哪项阵容条件影响排序。
5. **保持轻量和可停用。** 不录制视频；数据变化才重算／重绘；未知或过期事件隐藏提示；对照测量后台 CPU、内存和游戏帧时间。OP.GG 官方也说明 Enhanced Overlay 在不同机器上可能更慢，不能假设 SDK 自动解决性能问题。[官方性能排查](https://help.op.gg/hc/en-us/articles/48463517332249-The-app-is-lagging-or-dropping-frames)

暂不优先加入桌宠、语音陪玩、录像、社交、全模式百科或自动选择／购买。它们不能补上本项目当前最关键的候选识别、完整状态和按场景显示，而且会增加维护与运行成本。

Overwolf 接入实验应分别记录“运行时能启动”“游戏能检测”“所需 feature 可启用”“真实候选／选择事件收到”“国服多局可用”，不把前一步的成功当成后一步的证明。其公开 LoL 字段以及当前边界见 [无截图调研](NO_CAPTURE_RESEARCH.md)。
