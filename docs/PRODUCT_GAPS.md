# 产品差距与可借鉴方案

项目状态更新：2026-11-03，Hexthon v0.3.0。`npm start` 仍为无画面采集的接口模式；`npm run start:assist`（`--assist`）开启新轻量识别与场景浮层。下文竞品资料核查截至 2026-11-02，其能力来自官网、帮助中心或发布说明，未在本机腾讯国服逐项验证；“未核实”不表示对方一定没有。商业产品未公开采集实现时，不推测它使用了截图、进程内存或某个 SDK。

## v0.3.0 已接入的迭代

- 三卡路径使用指定前台游戏窗口的按钮条带与标题条，有限重读未识别标题；精确识别并取得两次独立画面后才显示卡片附近的推荐。过期画面、窗口变化和不完整名称不作为新证据。
- 商店路径优先合并顶部标题区域，单独验证底部控件；连续两次新鲜识别后显示。布局根据空位选择约 190–300 宽的侧栏或 96 高的横条，没有空间就隐藏。按键提示只加快检查，不等于商店已打开。
- 部分已选记录支持可靠局 ID／英雄匹配后恢复、换局清空、证据等级、槽位替换以及手动校正与撤销。HUD 使用独立后台线程，两次稳定匹配才入库；通常每 20 秒复核，选择、等级或窗口变化可提前触发。共用图标和未确认槽位不猜测，`complete` 始终为 `false`。
- 选人提示仅在确认 Mayhem、客户端前台且客户端旁有桌面空位时出现。已有自动英雄、队友、共享池跟随与 OP.GG 资料；无空位时仍可打开面板查看。
- 出装与强化规则扩展到部分明确装备前置、任务奖励、互斥和属性转换保护。规则依据已读取的信息解释排序变化，不把部分强化记录当作完整构筑。

上述功能已接入代码与离线流程。`test:light` 以合成数据和隐藏窗口覆盖卡片→选择→商店→关闭／换局；真实 ROI 性能探针也已运行，但返回 `NO_FOREGROUND_LEAGUE`，采样列表为空、没有捕获任何像素。这些结果不能证明国服实局识别率、FPS 改善或“不卡顿”。

## Hexthon 仍缺少什么

| 优先级 | 缺失或不完整的能力 | 当前情况与完成标准 |
| --- | --- | --- |
| P0 | 国服实局识别与性能验证 | 新轻量路径已接入并通过离线流程，尚需多局检查三卡、选择、商店、HUD 与关闭时机；补充分辨率、缩放、多屏及游戏显示模式验证。性能探针本次没有采到像素，还缺真实采集耗时和游戏帧时间对照。 |
| P0 | 完整已选海克斯 | 已完成按可靠局 ID 恢复部分记录和稳定槽位替换，但这不能补出从未观察到的强化。技能 API 仅覆盖部分强化，HUD 对共用图标、遮挡和未知布局会拒绝；未覆盖的普通被动及转化仍需可靠来源，始终标 `complete: false`。 |
| P0 | 无截图的候选、刷新与完整状态来源 | 默认 API 模式仍没有三选一或商店状态；助手模式采用局部画面识别，不能称为无截图方案。Overwolf 仅完成独立运行时试验，缺凭据时 GEP 未 ready，未验证国服真实事件，也未接入主应用。 |
| P1 | 场景定位的实际兼容性 | 已有卡片、商店和选人浮层，以及无空位隐藏、过期失效和前台校验。还需验证国服不同 UI 缩放、商店位置与遮挡下的实际显示，不能把合成画面通过当成全部布局可用。 |
| P1 | 装备与海克斯的完整构筑推理 | 已有双方装备对策和部分已知强化的前置、任务、互斥、属性转换与联动规则；仍缺全面组合覆盖、状态变化和流派切换建模及效果验证。敌方海克斯没有可靠来源，不参与假设性的“最优出装”计算。 |
| P1 | 原生商店推荐集 | 已有纯数据生成与保留其他装备页的合并函数，未接入写入。需验证国服读写、读回、恢复及本局是否热更新。 |
| P1 | 可核查的胜率、样本量与阵容模型 | OP.GG 页面目前只采用能核实的档位、排名和路线。缺少已核实胜率／样本量；职业标签的阵容修正不等于“最优五人阵容”或获胜概率。 |
| P1 | 刷新次数与收益 | 没有可靠刷新次数；当前参考只比较同品质已知档位和规则分，且以仍有次数为前提。尚不能给出实际刷新收益或选择概率。 |
| P2 | 正式分发与维护 | 当前源码启动可用；仍需可靠签名发布、更新和回退、版本不兼容诊断，以及游戏更新后的快速验证。 |

上述差距依据 [README](../README.md) 和当前实现。自动跟随英雄、选人己方阵容与共享池、双方公开装备、OP.GG 缓存、自绘面板及未知数据保护已具备。默认 API 模式不会因旧设置或接口失败开启采集；旧 `--visual-experimental` 全窗口视觉流程保留为历史实验，不是 `--assist` 的运行路径。既有 [OCR 性能记录](OCR_PERFORMANCE.md) 记录离线实验，不替代本版实局验证。

## 当前结构与后续原则

以下结构已部分落地，后续继续按这些原则补齐；它们不是对竞品未公开源码的描述：

1. **把信息来源和显示方式分开。** LCU 负责选人／阶段，Live Client 负责已公开装备；Overwolf 若实验成功，只补上它实际提供的事件。OP.GG 保持统计和推荐路线来源。
2. **按局保存有证据的状态。** 已实现可靠局 ID 匹配、部分记录恢复和校正撤销；继续区分候选、重随、已选、替换与结束。重启恢复已有记录不等于恢复完整历史，只收到“最近选中”也不能推导完整构筑。
3. **有场景证据才显示。** 强化提示贴近三张卡，关闭或过期即隐藏。商店已采用独立标题与控件验证，选人提示受模式及桌面空位限制；仍需实局确认布局，不以按键、三选一或 Tab 事件代替商店显示状态。
4. **推荐给出可检查的理由。** 区分 OP.GG 档位、统计胜率和本地规则分；说明是哪件敌方装备、哪个已知强化或哪项阵容条件影响排序。
5. **保持轻量和可停用。** 不录制视频；数据变化才重算／重绘；未知或过期事件隐藏提示；对照测量后台 CPU、内存和游戏帧时间。OP.GG 官方也说明 Enhanced Overlay 在不同机器上可能更慢，不能假设 SDK 自动解决性能问题。[官方性能排查](https://help.op.gg/hc/en-us/articles/48463517332249-The-app-is-lagging-or-dropping-frames)

暂不优先加入桌宠、语音陪玩、录像、社交、全模式百科或自动选择／购买。它们不能补上本项目当前最关键的候选识别、完整状态和按场景显示，而且会增加维护与运行成本。

Overwolf 接入实验应分别记录“运行时能启动”“游戏能检测”“所需 feature 可启用”“真实候选／选择事件收到”“国服多局可用”，不把前一步的成功当成后一步的证明。其公开 LoL 字段以及当前边界见 [无截图调研](NO_CAPTURE_RESEARCH.md)。
